`openstep dev` は、agent の実際の開発用データにつないだまま、App を自分のコンピューターで起動します。各 App の起動方法は、`openstep.config.json` というファイルで伝えます。

## 準備

1. agent フォルダーに `openstep.config.json` を作成します。実行したい App ごとに、App キーを名前にしたエントリを 1 つ追加します。

   ```json
   {
     "apps": {
       "web": {
         "cwd": "apps/web",
         "frontend": { "command": ["npm", "run", "dev", "--", "--port", "5173"], "port": 5173 },
         "backend": { "command": ["node", "functions/server.js"], "port": 8787 }
       },
       "admin": {
         "cwd": "apps/admin",
         "frontend": { "command": ["npm", "run", "dev", "--", "--port", "5174"], "port": 5174 }
       }
     }
   }
   ```

   - `cwd` は App のフォルダーで、agent フォルダーからの相対パスです。
   - `frontend` と `backend` はそれぞれ `command` と `port` を取ります。`command` はリストで、最初がプログラム、続いて引数です。`cwd` の中で実行されます。
   - バックエンドは、環境変数 `PORT` に自分の `port` を設定して実行されます。シェルで `PORT` を設定していても同じです。`PORT` で待ち受けるサーバーなら、ほかに何も必要ありません。
   - フロントエンドだけの App では `backend` を省略します。
   - プロセスごとに別のポートを割り当てます。

   App に実際にあるスクリプトとポートを使ってください。`package.json` を確認します。上のものは例にすぎません。

2. 各 App の依存関係を、その App のフォルダーでインストールします。

   ```sh
   cd apps/web
   npm install
   cd ../..
   ```

## 実行

1. agent フォルダーから、設定にあるすべての App を起動します。

   ```sh
   openstep dev
   ```

   1 つの App だけを起動するには：

   ```sh
   openstep dev --app web
   ```

2. CLI が各 App のアドレスを表示します。そのアドレスをブラウザーで開いてください。フロントエンド自身のポートは開かないでください。CLI が表示するアドレスが、App をプラットフォームにつなぐものです。
3. エディターで `apps/web` のファイルを編集します。フロントエンドの開発サーバーが、通常どおり変更を反映します。
4. 止めるには Ctrl-C を押します。CLI がプロセスを停止し、接続を解放します。

## 公開中のサイトのルール

バックエンドのある App では、`openstep dev` は `/api` を公開中のサイトのルールで扱います。そのため、公開中のサイトで失敗するリクエストの大半は、自分のコンピューターでも失敗します。下の 404 や 413 のどれかで最初に応答したとき、または下のヘッダーのどれかを最初に取り除いたとき、CLI は `openstep:` で始まる警告を表示し、何を変えるべきかを伝えます。各ルールについては、[公開中のサイトでの動作の違い](/ja/cli/bring-your-code/#公開中のサイトでの動作の違い) で説明しています。

- ページが `fetch`、`XMLHttpRequest`、`sendBeacon` で行う呼び出しは、いつもどおりサーバーに届きます。
- 素の `/api` URL を、それ以外の方法で読み込むと、公開サイトと同じく 404 になります。たとえば、コンポーネントが描画する `<img>`、リンク、フォーム、`window.location` です。そのような URL は、`src/lib/runtime` の `releaseRuntimePath('/api/...')` で作ってください。`openstep dev` では、これは `/_releases/openstep-dev/_generations/1` の下のパスを返し、CLI はそれを素のパスにしてサーバーに送ります。
- HTML や CSS のファイルに書かれた `/api` の URL も 404 になります。この場合、`openstep dev` は、そうした URL を書き換える公開中のサイトより厳格です。代わりに、スクリプトで `releaseRuntimePath()` を使って URL を設定してください。
- App の `src/lib/runtime.ts` がこのチェックより前のバージョンの場合、それらの読み込みは警告付きでサーバーに届きます。`openstep pull` を実行してください。プラットフォームのファイルの現在のバージョンが、フォルダーに戻ります。push のたびにも同じことが行われます。
- `text/event-stream` を求める `/api` リクエストは、すべて 404 になります。サーバーがレスポンスを終えれば公開中のサイトが応答するはずの `fetch` でも同じです。`/api` への WebSocket も 404 になります。
- ブラウザーとサーバーの間を通るのは、公開中のサイトが通すヘッダーと、ボディを送られたとおりに運ぶ `Content-Length`、`Transfer-Encoding`、`Content-Encoding` だけです。CLI は、`Cookie`、`Set-Cookie`、`Location`、`Content-Disposition` を取り除いたときに警告します。
- 10 MiB を超えるリクエストボディは 413 になります。
- `curl` などのプログラムは `Sec-Fetch-Dest` ヘッダーを送らないので、読み込みに対する 404 は、それらには当てはまりません。

App のそれ以外の部分、たとえばページやファイルは、そのまま配信されます。バックエンドのない App には、これらのルールはありません。公開中のサイトと同じく、その `/api` はフロントエンドに送られます。

## 知っておくこと

- 実際のデータです。ローカルでの実行は、作業ページでの App のプレビューと同じ開発用データを使います。実行した SQL はそのデータを変更します。使い捨てのコピーではありません。[サイトのデータ](/ja/build/data/) を参照してください。
- SSU がかかります。AI、メール、チェーン呼び出しなどのプラットフォームの機能は、App が自分のコンピューターで動いていても、通常どおり課金されます。[残高を確認する](/ja/account/balance/) を参照してください。
- サーバーは、あなたを訪問者として扱います。各 `/api` リクエストには、CLI にサインインしたウォレットが、`x-steps-user-address` ヘッダーで付きます。ブラウザーでも同じウォレットを接続してください。
- CLI が表示したアドレスは、別のサイトからのリクエスト（`Origin` がそのアドレスでないもの）と、そのアドレスに別の名前でアクセスしたリクエスト（たとえば `127.0.0.1` ではなく `localhost`）に、警告なしで 403 を返します。これは、ほかのページにローカルの認証情報を使わせないためです。
- シークレットをソースに入れないでください。CLI は、実行ごとに専用の認証情報と、その App の環境値を渡します。値を設定するには、[App、データ、コントラクト](/ja/cli/apps-data-contracts/) と [環境値](/ja/build/environment-values/) を参照してください。
- 起動するすべての App には、`openstep.config.json` にエントリが必要です。すべての App を起動したときにエントリのないものがあると、コマンドは停止して、その App 名を示します。
- 設定したプロセスのどれかが終了すると、`openstep dev` は起動したすべての App を停止し、コマンドを終了します。終了コードが 0 以外の場合は、`App runtime exited with code N` というエラーで終わります。原因は、失敗したプロセス自身の出力を読んで確認してください。
- 設定内のパスは、agent フォルダーの中に収まっている必要があります。
- `openstep.config.json` はローカル専用です。`push` では送られません。
