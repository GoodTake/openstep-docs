## 構成要素

| 要素 | 役割 |
|---|---|
| ユーザーと訪問者 | Agent とチャットしてものを作る人、クラスを運営する講師、公開された App を使う受講者。 |
| エッジ | すべてのリクエストを HTTPS で受け、ドメインで振り分ける。行き先は builder サイトか、公開された App。 |
| プラットフォームサービス | ウェブ UI と API。サインイン、Agent、会話、Publish、コースページ。 |
| プラットフォームデータベース | PostgreSQL。Agent、会話、すべてのターン、すべての構築実行を保持する。 |
| Agent フレームワーク | Product → Agent → App。凍結された Product の版がルール、手法、Skills を決める。そこから作った Agent は、会話と計画を受け持つ一つの制御面と、一つ以上の App を持つ。 |
| 構築オーケストレーション | 大きな依頼を計画として実行する。計画、人による承認、タスクごとの構築・チェック・レビュー・修正、最後に最終レビュー。 |
| builder サンドボックス | Agent ごとに一つの隔離コンテナ。ターンごとにコードを借り受け、終われば返す。キーも git 履歴も持たない。 |
| モデルゲートウェイ | すべてのモデル呼び出しはプラットフォームを通り、タスクごとにモデルの階層が選ばれる。GPT-6、Opus、DeepSeek などの最先端モデルを使う。 |
| App ランタイム | 構築中はプレビュー、公開後は本番。フロントエンドは静的ファイルとして配信され、バックエンドはオンデマンドのコンテナで動く。 |
| App データベース | App ごとに独自のデータを持ち、開発用と本番用は分かれている。Publish は常にデータを残す。 |
| 機能ゲートウェイ | 動いている App がプラットフォームに頼めること。AI、メール、オンチェーン取引、スケジュールタスク。利用料は SSU で課金される。 |
| 外部サービス | Base チェーン、接続した SaaS アカウント、MCP サーバー。必ずプラットフォーム経由で使う。 |

## 三つのストーリー

インタラクティブな図の **Guided views** で、それぞれを一歩ずつ再生できます。

### 一文がコードになるまで

1. 誰かが Agent に一文を入力する。
2. プラットフォームがターンを確認し（権限、残高、構築がすでに実行中でないか）、記録する。
3. Agent フレームワークがこのターンの指示、Skills、MCP を組み立て、コードを builder サンドボックスに貸し出す。
4. builder はモデルゲートウェイ経由でモデルを呼び、コードを編集し、プレビューを確認する。
5. ターンが終わるとコードはプラットフォームに戻り、プラットフォームがコミットする。

### 受講者: コースを受ける

1. 講師が参加リンクを共有する。受講者はウォレットでサインインして参加する。
2. コースページには本番の App が埋め込まれている。受講者は何も構築しない。
3. 受講者の操作はすべて、クラスで共有する App のデータに書き込まれる。
4. オンチェーンの操作は App のバックエンドが機能ゲートウェイ経由で送る。手数料は講師に課金される。

### 講師: クラスを運営する

1. 講師はコース用の Product から Agent を作り、クラスを開く。
2. コースへの変更は、実データで動く候補版として構築される。本番に出る前に共同作業者がレビューする。
3. 講師は参加リンクを共有し、誰が参加したかを確認する。
4. 新しい学期は **Start a new session** で始める。業務データと進捗はリセットされ、メンバーは残る。

## 設計の原則

- **すべての Agent に同じ構造。** ユーザーが始められる体験は、すべて Agent Product です。作者はルール、手法、Skills を版として凍結し、プラットフォームがターンごとにそれらを builder 向けに組み立てます。
- **二段階の制御。** 一文は、モデルによる一回のツールループです。大きな依頼は、プラットフォームが一歩ずつ進める計画になります。Agent のすべての App は一緒に本番に出て、Publish がデータを削除することはありません。
- **厳格なセキュリティ境界。** サンドボックスはコードを借りるだけです。キー、git コミット、上流のモデルキーはプラットフォームに残り、外部アカウントのトークンはプラットフォーム経由でしか使われません。
